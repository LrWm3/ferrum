# Direct pilot service lifecycle observations

Evidence: `/tmp/ferrum-stage5-prusti-pilot-v4/logs/000002-jvm/server.log` (positive, two requests), `000003-native/server.log`, and their `service-cleanup.json` files. The pilot used one service process for each two-request block and both requests completed. JVM log prints “Starting: JVM startup” twice but emits the “Using JVM ... Java 17.0.21” initialization message only on the first. The source explains the distinction: `prusti-server/src/verification_request.rs` declares `VIPER` as `OnceLock<Viper>` and the labeled startup scope calls `VIPER.get_or_init(...)` for each request. The second label is the same lookup scope, not evidence that a new JVM started. Each request then attaches a thread and constructs JVM objects. The server invokes `new_viper_verifier` in the verification-request processing path for each request; the log shows a verifier-startup scope and Silicon 6b540aa4/Z3 identification in each. This supports reuse of the process-level Viper/JVM object and repeated verifier construction, not a claim that all JVM or solver internals are cold or warm.

In `prusti-server/src/native_backend.rs`, `verify_internal` constructs `native_frontend_with_warning_sink` within each request, calls verification and stops it. The native pilot log shows a verifier-startup scope for both requests. This is evidence of a fresh native frontend setup per request within a persistent server process; it does not prove that no state is shared elsewhere or establish JVM/solver CPU timing. The native stopwatch labeled verifier startup surrounds more work than the JVM label: its log contains backend-verification phase before the startup scope completes, so those labels must not be compared as equivalent durations.

All four pilot service cleanup records reported `stopped: true`, no pending children and no error; two JVM `leader_exit` values were 143 and two native values -15 after requested termination. The supervisor tracking is limited to observed descendants. The configured source/native Z3 executable path and JVM bundle appear in JVM logs; cache policy is represented by runner environment/options and not independently fully exposed in these log lines. None of these pilot durations is a performance result.
