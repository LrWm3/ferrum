# Direct Prusti measurement package

This package contains the hardened direct-Prusti runner, owned-session and service supervisors, workload definitions and a prepared-input example. The bounded pilot v4 completed with 12 valid requests; its scope and earlier failed or interrupted attempts are recorded below. The pilot is a harness check, not a performance result. The tools are relocatable as a group; `prepared.example.json` retains absolute paths to the actual frozen source, seed targets, binary artifacts and calibration logs, so moving the data requires updating and rehashing a new prepared manifest. They are not a self-contained archive of those artifacts.

The final Prusti build source is `a59ed917c1c3c4c4ca6ff1de12ad20d48491d021`, PCG `c18a51899e37e0fa67f9b5f17f7d518ef2f5518c` and Ferrum `afdf10cf59106c38d09df32939f1aa9c77d0b989`. The external `calibration-summary.json` records four untimed one-worker, branch-off native/JVM pairs: three expected successes and the line-8 expected assertion failure, all with byte-identical paired Viper dumps and one encoding/conversion/verification phase event each. Each clean checked only the root fixture package; no specs-library rebuild was observed. The first marker-less clean failure is preserved in `/tmp/ferrum-stage5-prusti-inputs/calibration/observation_pass-native/`. None of those calibration durations is performance evidence.

The primary configuration disables the outer Prusti result cache (`PRUSTI_ENABLE_CACHE=false`) and keeps Silicon internal caches at their production default, on. The runner rejects an internal-caches-off declaration and accidental `--disableCaches` from the supplied environment. Stage 4 compatibility sessions hardcoded `--disableCaches`; they are a different policy and must not be treated as the primary performance baseline. A future internal-caches-off control must be separately labeled. The bundled Prusti JVM `viperserver.jar` (hash in prepared input; historical Silicon 6b540) is distinct from the standalone Silicon ff386 reference. Actual backend options and configuration files should be independently checked; a manifest declaration does not prove effective configuration.

## Minimal bounded end-to-end pilot

The successful pilot used the command below. Its output directory now exists; repeat only into a new output directory and only with the coordinated solver slot:

```sh
python3 tools/performance/prusti/run.py \
  --prepared /tmp/ferrum-stage5-prusti-package/prepared-final.json \
  --cases tools/performance/prusti/pilot-cases.json \
  --output /tmp/ferrum-stage5-prusti-pilot-v4 \
  --pilot --pairs 1 --seed 42 --workers 1 --branch off \
  --mode fresh service --requests 2 --verifier-timeout 180 --outer-timeout 300 --port 60861
```

Pilot v4 retained all 12 valid effective requests, one event per phase, no dependency rebuilds, four clean service audits and unchanged frozen artifacts. JVM logs identify the bundled Silicon 6b540aa4 and configured Z3. Both backends logged verifier startup for each service request, so later requests establish service reuse only, not necessarily verifier reuse. The earlier v1 JVM service failed due to missing standalone-server configuration; v2 was interrupted after the coordinator requested unique ports; v3 stopped after a harness scheduling bug. All are preserved separately under `/tmp/ferrum-stage5-prusti-pilot-v{1,2,3}`. Only tools changed; no runtime source was changed.

The output directory must not exist. This schedules the positive `observation_pass` and negative `mut_element_array_wrong` for both backends: four fresh requests and four separate service blocks with first and later requests, 12 requests total. The complete block schedule, backend order and distinct per-service endpoints are randomized or assigned from the declared seed and base port, then written before the first run. The runner checks port-range bounds and never kills an unrelated listener. `--pilot` allows one pair; pilot results are a harness check, not performance estimates. Verify all 12 expected outcomes, exactly one event for each named phase, no unexpected library rebuild, complete owned-process and service cleanup, correct final artifact/seed hashes, and both valid expected-negative diagnostics at Rust line 8. Do not proceed to timed repetitions if any observation is invalid, timed out, incomplete or missing. Retain all results and failure logs; do not replace them with retries.

The runner records host metadata and before/after request load snapshots. It accepts exactly one Cargo `Checking` event for the root fixture and invalidates any extra `Checking` or `Compiling` dependency event. GNU time parsing requires exactly five unique fields with finite nonnegative wall/user/system values and integer RSS and exit status; raw timer files are retained. The runner copies each immutable seed to its own scratch directory, writes the standard Cargo `CACHEDIR.TAG` only into that owned copy, then runs `cargo clean -p` against it before invoking final `cargo-prusti`. It uses GNU time and the owned session supervisor for each client. Successful verification requires the expected Rust exit and error/location as well as exactly one `Rust to VIR encoding`, `VIR conversion` and `backend verification` log event; absent or ambiguous events are invalid. Outer timeouts are censored. `trials.jsonl` preserves raw row classifications; `effective-trials.jsonl` downgrades every request from a service block if its cleanup audit fails, and `summary.json` exposes both sets and invalid block IDs. For any timing analysis, use effective records and independently inspect the service cleanup and frozen-artifact postflight.

Fresh mode includes process startup and does not clear the OS page cache. Service launch-to-socket time is not proof that the backend or solver is initialized; first and later requests remain distinct. GNU time reports hundredth-second wall/user/system fields and maximum RSS for the timed client process tree; it does not include CPU of a still-running external service or necessarily capture every descendant. Native verification spans include `frontend.verify`; JVM spans include `backend.verify` and wrapper/polling. They are inclusive and not identical. There is no exclusive frontend, symbolic execution, or Z3 time. Worker and solver lifetimes overlap; do not add or subtract their elapsed times as sequential wall phases. Supervisor PID/start-time tracking reduces orphan risk but cannot prove capture of every rapidly escaping descendant. Failed/timeout/cleanup-incomplete observations are not successful durations.
